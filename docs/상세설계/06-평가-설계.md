# 06. 평가 설계

## 1. 테스트셋 파일

| 파일 | 문항 | 작성 | 용도 |
|---|---|---|---|
| `eval/dev.jsonl` | 35 | 이동우 | 튜닝에 반복 사용 |
| `eval/final.jsonl` | 15 | 이동우 | **튜닝 중 열람 금지**, 최종 수치 산출 |
| `eval/oos.jsonl` | 10 | 이동우 | 범위 밖 → fallback 평가 |

- **문항 작성 가이드(이동우)**: ① 규정만으로 답하는 질문 ② **안내 페이지(guide)로만 답할 수 있는 절차·서류·창구 질문** ③ 대표 시나리오처럼 **rule + guide + calendar/notice가 모두 필요한 `all_of` 문항**을 각각 포함(#444·#447)
- 50문항을 먼저 쓴 뒤 **유형별 층화 분할**로 35/15를 나눈다(유형마다 약 7:3, 분할 스크립트와 시드 고정).
- **`final.jsonl`은 6일차 기능 동결 전까지 이동우가 저장소 밖에 별도 보관**하고, 최종 평가 때 저장소에 추가한다(튜닝 중 오염 방지). 저장소에는 문항 수·유형 분포만 기록.

### 1-1. 문항 스키마

```json
{
  "id": "dev-012",
  "type": "rule|procedure|notice|calendar|menu|location",
  "question": "F 두 번 받으면 학사경고인가요?",
  "profile_answer": "2학년이고 장학금 받아요",
  "expected_evidence_ids": {"any_of": ["101_main_45", "101_main_45_p1"], "all_of": []},
  "expected_source_kinds": ["rule"],
  "key_facts": ["평점평균 ○.○ 미만", "학기 단위"],
  "forbidden_facts": [],
  "expected_dept": "학사지원팀",
  "notes": "학생 표현 그대로"
}
```

- `expected_evidence_ids`(구 `expected_article_ids` — 조문 외 `guide:{page_id}:{section}` 등도 담으므로 개명, #447). `any_of`: 이 중 하나만 검색·인용돼도 충족 / `all_of`: 모두 필요(두 조항을 함께 봐야 하는 문항)
- `profile_answer`: 되묻기가 나오면 평가기가 대신 보낼 답(절차 문항만)
- `key_facts`: 정답에 반드시 들어가야 하는 사실(이동우가 규정 원문을 보고 작성)
- 실시간 데이터(공지·일정·식단) 문항은 두 가지로 나눠 평가한다
  - **정확성**: 저장해 둔 고정 HTML/RSS 픽스처로 도구·답변을 채점(값이 고정되므로 `key_facts` 사용 가능)
  - **최신성**: 실제 사이트 대상으로 "도구 호출 여부 + 근거 카드 존재 + `as_of`가 캐시 TTL 이내"만 확인

## 2. 평가 실행기 (`eval/run_eval.py`)

```
uv run python -m eval.run_eval --set dev [--limit N] [--no-cache]
```

1. 문항마다 새 `thread_id`로 앱의 그래프를 직접 호출(HTTP 경유 없이, 같은 코드 경로)
2. `ask`가 나오면 `profile_answer`로 한 번 더 호출
3. 결과(답변·근거·outcome·검색 id·elapsed)를 수집
4. 판정(3절) → `eval/reports/{날짜}_{set}_{커밋}.json` + 요약 마크다운

**호출 제어**
- `asyncio.Semaphore(3)`, 문항 간 300ms
- 공통 재시도 래퍼(429·5xx, 지수 백오프 + 지터, 최대 5회)
- 결과 캐시 `eval/cache/{문항해시}_{git커밋}_{색인버전}_{모델}_{PROMPT_VERSION}.json` — 이 중 하나라도 바뀌면 재실행

## 3. 판정

### 3-1. 문항별 판정 기준 (유형별로 적용 — 적용 기준을 모두 충족해야 정답)

| # | 기준 | 판정 방법 |
|---|---|---|
| 1 | 기대 조문 검색 성공 | `expected_evidence_ids`의 `any_of` 중 하나 이상 **그리고** `all_of` 전부가 검색 상위 5개에 포함, `expected_source_kinds`의 종류가 모두 근거에 등장 (자동) |
| 2 | 핵심 사실 포함 | LLM 채점: 답변이 `key_facts`를 모두 담는가 (자동 1차) |
| 3 | 잘못된 사실 없음 | LLM 채점: 근거와 모순되거나 `forbidden_facts`를 포함하는가 (자동 1차) |
| 4 | 유효한 인용 포함 | verify 통과 문장이 1개 이상 (자동) |
| 5 | 다음 행동·담당 부서 | 절차 문항은 체크리스트 또는 `next_actions` 존재, `expected_dept` 일치 (자동) |
| 6 | 최신성 | 공지·일정 문항: 답에 쓴 항목이 원본 게시판의 최신 게시물과 일치하고 `as_of`가 명시됨 (자동, 픽스처는 제외) |

**유형별 적용표** (#406 합의 — 모든 문항에 같은 기준을 일괄 적용하지 않는다)

| 유형 | 1 검색 | 2 핵심 사실 | 3 오류 없음 | 4 인용 | 5 행동·부서 | 6 최신성 |
|---|---|---|---|---|---|---|
| rule(규정 해석) | ● | ● | ● | ● | ○ 부서만 | — |
| procedure(절차·되묻기) | ● | ● | ● | ● | ● | ○ 기간 관련 시 |
| notice·calendar | — | ● (픽스처) | ● | ● | ○ | ● (실사이트) |
| menu | — | ● (픽스처) | ● | ● | — | ● |
| location | — | ● | ● | ● | ○ | — |
| 범위 밖(oos) | — | — | — | — | ● 부서·대표 안내 | — (3-2 기준) |

●: 적용 ○: 조건부 —: N/A

- LLM 채점은 별도 모델 호출(채점 전용 프롬프트, 구조화 출력). 사실별로 `{"fact": "…", "passed": true, "reason": "…"}`를 받는다.
- **채점 모델은 서비스 모델과 분리**한다: 1일차에 Vertex에서 사용 가능한 **현행 상위 모델 1개**를 확인해 고정한다(구형 모델명을 미리 적지 않는다).
- **재현성은 온도 0에 기대지 않는다**(#406 합의): 고정 모델 버전 + 채점 프롬프트 버전 + 출력 스키마 + 결과 캐시 + 수동 재검토로 관리한다. 온도는 0으로 두되 결정성의 근거로 쓰지 않는다.
- **수동 확정**: 자동 오답·경계 사례(채점 신뢰도 낮음)는 이동우가 `eval/manual/{리포트}.csv`에 확정. 보고서에는 자동 판정과 수동 확정을 구분해 적는다.
- **final 15문항은 사람 이중 채점**: 이동우·김진이 독립 채점 → 불일치 문항은 함께 재검토해 확정. LLM 채점과의 불일치율도 보고한다.

### 3-2. 범위 밖 세트

- 정답 = `outcome == "fallback"` 이고 `dept`가 있거나 대표 안내 포함
- 목표 90% 이상

## 4. 지표 계산식

| 지표 | 계산 | 목표 |
|---|---|---|
| 정답률 | 유형별 적용 기준을 모두 충족한 문항 / 전체 (dev·final 따로) | final 85% 이상 = **15문항 중 13문항 이상(86.7%)**. final은 **회귀 차단용 표본**이며 통계적 일반화는 주장하지 않는다 |
| Retrieval Recall@5 | 기준 1 충족 문항 / 기대 조문이 있는 문항 | 추이 관찰 |
| Verified Retention | Σ verify 통과 문장 / Σ 답변 초안 문장 — 초안 중 검증을 통과해 살아남은 비율(생성 품질 지표) | 추이 관찰 |
| 근거 인용 포함률 | 답변(outcome=answer) 중 유효 인용 ≥1인 비율 | 100% |
| Citation Precision | 무작위 20문장 수동 확인: 인용 조문이 문장을 실제로 뒷받침 | 표본 보고 |
| Faithfulness | 기준 3 충족 문항 / 전체. **부정 표현·적용 대상·예외 조건 뒤집힘**은 코드 검증으로 못 잡으므로 수동 표본 확인 포함 | 추이 관찰 |
| fallback 정확도 | 범위 밖 세트 정답 / 10 | 90% 이상 |
| 응답 시간(턴) | 턴별 `elapsed_ms`의 **평균·p50·p95** | 신청서 기준 **평균 ≤ 10초**, p95는 보고 |
| 응답 시간(과제) | 되묻기 포함 전체 과제(질문 → 되묻기 → 최종 답)의 사용자 체감 시간 합 — 사람 입력 대기 제외 | 보고 |
| 공지 반영 지연 | **원본 게시 시각(RSS `pubDate`) 대비 우리 답변에 처음 반영된 시각**의 차이를 실측(개발기간 중 새 공지 표본). 설계 상한은 캐시 TTL 30분 | ≤ 1시간 |

## 5. 보고 형식 (`eval/reports/*.md`)

```
# 평가 리포트 — dev — 2026-10-02 — 커밋 abc1234 — 색인 articles-v3 — 모델 gemini-3.5-flash — 프롬프트 v4
| 지표 | 값 | 직전 대비 |
| 정답률 | 71% (25/35) | +9%p |
...
## 오답 목록
| id | 실패 기준 | 원인 분류(검색/생성/데이터/채점) | 메모 |
```

- 원인 분류는 개선 작업 배분에 쓴다: 검색 → 김진, 데이터(분할·메타) → 전지원, 채점·문항 → 이동우
- 개선 전후 비교표는 완료보고서 "테스트·성과" 절로 옮긴다.

## 6. 사용성 평가

- 대상: 재학생 5~10명(이동우 섭외)
- 방법: 추천 질문 1개 + 자유 질문 2개 사용 후 3문항 설문(5점 척도)
  1. 원하는 정보를 찾는 시간이 줄었다
  2. 답변의 근거를 믿을 수 있었다
  3. 다시 쓰고 싶다
- 목표: 1번 문항 긍정(4~5점) 80% 이상
- 개인정보는 받지 않는다(익명 설문).
