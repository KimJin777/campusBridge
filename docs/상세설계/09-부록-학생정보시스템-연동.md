## 1. 교수님 구상 — 도구 하나 추가로 붙인다

```text
학생(로그인) ─▶ classify: evidence_needs(규정 등) + personal_data_needs(예: 이수학점)
                    ▼
               plan_tools(결정적) ─ 병렬 ─┬─ search_academic_knowledge  (공개 규정)
                                          └─ get_my_academic_record     (학교 DB 읽기 전용 API) ← 추가될 도구
                    ▼
               compose: 규정 근거 + 본인 기록을 종합해 답변
```

- 학교 DB는 **읽기 전용 API**로만 접근한다(직접 DB 접속·임의 쿼리 없음).
- LangGraph 도구 체계에 `@tool` 하나(`get_my_academic_record(fields)`)를 추가하는 방식이다. 정확히는 **도구 추가 + 로그인 문맥 주입 + 개인 결과 분기**(원칙 7)가 필요하다 — "구조 수정 없이 도구만 추가"는 아니다(#471·#472).

## 2. 지금 지켜 둘 최소 원칙 (나중에 뜯어고치지 않기 위해)

| # | 원칙 | 이유 |
|---|---|---|
| 1 | 도구 인자에 **학번을 받지 않는다**. 누구의 기록인지는 **로그인 세션**에서만 정한다 | 모델이나 사용자가 다른 학생을 조회하는 사고(IDOR) 방지 |
| 2 | 요청 필드는 **허용 목록**(예: 학적 상태·학년·이수학점)만 | 필요 이상 조회 방지 |
| 3 | 개인 기록은 공개 근거(`Evidence`)와 **다른 타입**으로 다루고, **검색 색인·공유 캐시·관리자 통계에 넣지 않는다** | 공개 지식과 개인정보 분리 |
| 4 | 개인 기록이 들어간 턴은 **공개 턴의 90일 보존을 쓰지 않는다**(짧은 보존, 구체 기간은 연동 시 개인정보 담당 검토) | 파생 결과("6학점 부족")도 개인정보 |
| 5 | 졸업·장학 자격처럼 중요한 판정은 **계산 코드**가 하고 LLM은 설명만. 계산 기준은 **규정 조문·개정 버전에 묶고**, 규정이 개정되면 판정을 멈추고 검수 | 환각·옛 기준 사용 방지 |
| 6 | 로그인 없는 현재 MVP에서는 서버가 개인 기록 요청을 **항상 비운다**(모델 출력과 무관) | 프롬프트 약속에만 맡기지 않음 |
| 7 | 개인 기록 도구는 일반 `ToolResult`가 아니라 **`PrivateToolResult{facts: list[PrivateFact]}`** 를 반환하고, `run_tools`는 타입에 따라 **`private_facts` 임시 채널**로 분기 — `evidence`·SSE 근거 카드·`ToolMessage`·공용 로그에 넣지 않으며 compose 후 폐기. 로그인 주체는 모델 인자가 아니라 서버 실행 문맥에서 주입(#472) | 지금 구조의 도구 결과 경로(`evidence`)로 개인정보가 흘러가는 것 방지 |

## 3. 핵심 메시지와의 관계

현재 서비스는 "학교 시스템·부서 업무 무변경"으로 **이것만으로 완결**된다. 학교 DB 연동은 학교가 읽기 전용 API와 로그인(SSO)을 제공할 때의 **확장**이며, 그 단계에는 "업무 무변경" 주장을 적용하지 않는다.

## 4. 연동 시 할 일(메모)

- 학교 개인정보·보안 담당 검토, 이용 동의
- 로그인 방식(SSO) 확정 — 내부 식별자는 IdP의 불투명 ID 사용(학번 해시 금지)
- 위 원칙 1~6의 테스트(다른 학생 조회 불가, 개인 기록이 색인·로그·통계에 없음, 규정 개정 시 판정 중지 등)
