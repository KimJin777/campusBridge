## 0. 수집 원칙과 출처 목록 (#417~#425 토론)

### 0-1. 수집 승인 — robots.txt

- `www.kyungnam.ac.kr`·`yz.kyungnam.ac.kr`의 robots.txt는 일반 수집기(`User-agent: *`)를 `Disallow: /`로 막고 있다(2026-09-28 확인).
- **교수님 결정(#446, 2026-09-29)**: 대학혁신위원회 사업 범위의 기관 승인으로 보고 **해결된 것으로 진행**한다. 공문은 교수님이 별도 작성·전달하며 **개발·스파이크의 선행 조건이 아니다**. 수집은 **최초 1회 적재가 기본**, 필요할 때만 재수집(서버 부하 없음).
- **현재 모드: `approved`**(`COLLECTION_MODE`)

| 모드 | 용도 | 비고 |

| `approved`(**기본**) | 아래 출처 목록의 URL만 수집 | 식별 가능한 User-Agent, 요청 간격 ≥1초, 캐시·해시 변경 감지, **재귀 크롤링·로그인 영역 접근 금지**, 403/429·구조 변경 시 우회하지 않고 중단·확인 |

## 1. 규정 수집 파이프라인

```
list_rules ─▶ download_hwp ─▶ convert_text ─▶ split_articles ─▶ validate ─▶ build_jsonl ─▶ import_index
   (목록)        (원본 보관)       (hwp5txt)        (조 단위)        (검수)       (색인 문서)      (Vertex AI Search)
                                                                         └─▶ manifest 갱신
```

실행 형태: 로컬 CLI(`uv run python -m ingest.rules <단계>`) + 배포 후 Cloud Run Job. 웹 서비스 안에서는 실행하지 않는다.

### 1-1. `list_rules`

- 입력: 대상 편 목록(기본 `[2, 3]`, 설정값)
- 처리: 규정관리시스템(`https://yz.kyungnam.ac.kr/rule/`) 편별 목록 페이지 파싱
- 출력: `data/processed/rules.json`

```json
[{
  "rule_no": "101",
  "rule_name": "경남대학교 학칙",
  "part": 2,
  "revision_no": 66,
  "revision_date": "2025-03-01",
  "department": "학사지원팀",
  "hwp_url": "https://yz.kyungnam.ac.kr/rule/rdata/…/reg101_xxxx.hwp",
  "file_version": "xxxx",
  "rule_level": "학칙"
}]
```

> 규정번호 `101`은 **예시**다. 학칙의 실제 번호는 1일차 목록 수집에서 확인한다. (참고: `reg195`는 제1편 **학교법인 한마학원 정관**으로 확인됨 — `docs/참고/reg195_2365.hwp`)

- `rule_level` 판정: 규정명 끝말 기준 — "학칙" / "규정" / "시행세칙"·"세칙" / "지침"·"요령" / 기타. 위계 순서 `학칙 > 규정 > 시행세칙 > 지침 > 기타`
- 목록 페이지의 실제 구조는 1일차에 확인 후 선택자를 확정한다(현재 확인된 것: 7편 체계, HWP 링크 패턴, 개정일·차수·소관부서 표기).

### 1-2. `download_hwp`

- 요청 간격 ≥ 1초, User-Agent `CampusBridge/0.1 (contest; contact: 관리자 메일)`
- 저장: `data/raw/{rule_no}_{file_version}.hwp` (git 제외)
- 응답 헤더의 `ETag`·`Last-Modified`를 매니페스트에 기록
- 허용 도메인 외 URL은 거부(`yz.kyungnam.ac.kr`)
- HTML 목록 페이지 인코딩: 응답 헤더 charset이 없거나 깨지면 `EUC-KR/CP949`를 감지해 디코딩(`charset-normalizer` 폴백)

### 1-3. `convert_text`

- 1차: `hwp5txt <file>` (pyhwp **0.1b15, AGPL-3.0+** — 수집 파이프라인에서만 외부 명령으로 실행, 서비스 코드·저장소에 포함하지 않음)
- 실패(예외·빈 출력) 시 2차: LibreOffice `--convert-to txt` — **로컬 전용**(컨테이너에 넣지 않음, 07 문서)
- 결과: `data/interim/{rule_no}.txt`, 변환기 이름·버전을 매니페스트에 기록
- Windows 로컬 실행 주의: 한글 파일명 인자가 깨질 수 있으므로 저장 파일명은 `{rule_no}_{file_version}.hwp`(ASCII)로 한다. 출력은 `PYTHONUTF8=1`로 UTF-8 고정.

#### 실측 결과 (2026-09-28, `docs/참고/reg195_2365.hwp` = 법인 정관, 786줄)

| 관찰 | 설계 반영 |
|---|---|
| 조 머리 95줄 **전부** 본문 첫 문장과 같은 줄("제1조(목적) 이 법인은…") | 조 머리 뒤 남은 텍스트를 본문 첫 줄로 보존 |
| **표 내용은 출력되지 않고 `<표>` 한 단어만** 남음(3곳). 탭 0개, 괘선 없음 | `has_table` = 본문에 `<표>` 포함 여부. 표 내용은 원문 링크로 안내 |
| 삭제 조·절 16건: "제13조 <삭  제>", "제3절 … <삭  제>"(괄호 제목 없음) | 삭제 조 인식·색인 제외, 번호 연속성 검사에서는 존재로 인정 |
| 부칙 69개, 머리 공백 제각각("부   칙", "부    칙") | 부칙 머리 `^\s*부\s*칙` |
| 부칙 날짜 표기 제각각: `68. 1. 23 문교대…`(2자리 연도), `1998.  4. 25`, `2026. 8. 20. 2026학년도 제2차 법인이사회` | 관대한 날짜 파서 + 실패 시 부칙 순번 ID |
| 개정 주석 줄 "[본조신설 2022.4.27.]", 제목 뒤 "<개정 2021.3.30.>" | 본문에서 떼어 `notes` 메타데이터로 |
| 문서 머리 표제("定款", "學校法人 汗馬學園") | 첫 장·조 머리 전 줄은 버림 |
| 별표: "(별표 1)" 형식, 내용은 `<표>` | 별표 머리 `^\(?\[?별표\s*\d*` |
| 제목 속 중첩 괄호: 이 파일 0건 | 다른 규정 대비로 괄호 깊이 방식 유지 |

`hwp5html`로 표 내용을 추출할 수 있는지는 1일차에 확인한다(장학 기준표 등 표가 핵심인 규정이 있으면 필요).

**`parse_addenda_date`** — 부칙 머리 줄의 괄호 안 문자열 → 없으면 **부칙 머리 다음 1~2행**("이 규정은 2025년 3월 1일부터 시행한다." 등)에서 첫 날짜 추출(#406 합의: 시행일이 다음 행에만 있는 규정 대비)
- 패턴: `(\d{2,4})\s*\.\s*(\d{1,2})\s*\.\s*(\d{1,2})`
- 2자리 연도: `>= 50`이면 19xx, 아니면 20xx
- 다음 행 패턴: `(\d{4})\s*년\s*(\d{1,2})\s*월\s*(\d{1,2})\s*일`도 인식
- 실패하면 `None` → ID에 순번 사용(1-5절)

**그 밖의 규칙**
- 한 조의 본문 길이 > 2,000자 → 항 머리(①~⑳) 기준으로 서브 청크 분할. 서브 청크에는 조 머리(제목)를 앞에 붙여 문맥 유지
- `has_table` = 본문에 `<표>` 토큰 포함. `<표>` 토큰은 본문에서 "[표 — 원문 참조]"로 치환해 색인
- 부칙은 기본적으로 **최신 부칙 1~3개만 색인**(오래된 부칙은 시행일 이력이라 학생 질문과 무관) — 개수는 설정값

### 1-6. `validate` — 자동 검수

| 검사 | 기준 | 실패 시 |
|---|---|---|
| 조 번호 연속성 | 본문 조 번호가 1부터 빠짐없이 증가(가지번호 제외, **삭제 조도 존재로 인정**) | 경고 + 누락 번호 목록 |
| 첫 문장 보존 | 조 본문이 제목만 있고 비어 있는 비율 < 10% | 경고(머리 줄 본문 유실 의심) |
| 날짜 파싱 | 부칙 날짜 파싱 실패 건수 | 정보(순번 ID로 대체됨) |
| 조 개수 | 0개가 아니며, 이전 버전 대비 50% 이상 감소하지 않음 | **색인 갱신 중단**(기존 유지) |
| 본문 길이 | 조 본문이 비어 있지 않음 | 경고 |
| 부칙 분리 | 부칙 이후 조가 `main`으로 분류되지 않음 | 오류 |
| 비정상 길이 | 변환 텍스트가 이전 버전 대비 2배 이상 길어짐(중복·쓰레기 출력 의심) | 경고 + 색인 갱신 보류 |
| ID 중복 | `article_id` 중복 0건 | 오류 |

- 조 번호 결번은 삭제·개정으로 **정상일 수 있으므로** 연속성 실패는 경고로만 둔다.

결과는 `data/processed/validate_report.json`, 전지원 샘플 검수 대상 목록 포함.

## 2. 색인 문서 스키마 (Vertex AI Search)

`data/processed/articles.jsonl` — 한 줄 = 조문 1개

```json
{
  "id": "101_main_32",
  "structData": {
    "article_id": "101_main_32",
    "rule_no": "101",
    "rule_name": "경남대학교 학칙",
    "rule_level": "학칙",
    "article_no": 32,
    "article_branch": null,
    "article_title": "휴학",
    "chapter": "제5장 학적",
    "section": null,
    "kind": "main",
    "addenda_date": null,
    "department": "학사지원팀",
    "dept_id": "acad_support",
    "revision_date": "2025-03-01",
    "revision_no": 66,
    "source_url": "https://yz.kyungnam.ac.kr/rule/…",
    "has_table": false,
    "access": "public",
    "content_hash": "sha256:…"
  },
  "content": "(형식 미확정 — 아래 안 A/B 중 1일차 결정)"
}
```

> ⚠️ `content.rawText` 형식은 **쓰지 않는다.** Discovery Engine 문서의 `content`는 `uri`(GCS 파일) 또는 `rawBytes`(base64) 방식으로 알려져 있어, `rawText` 전제로 JSONL을 만들면 가져오기에서 실패할 수 있다(Codex 검토).

**가져오기 형식 후보 — 1일차 사전 검증에서 결정 (#406 합의: 안 B 먼저)**

| 안 | 방식 | 장단점 |
|---|---|---|
| A. 비정형 TXT | 조마다 `gs://{bucket}/articles/{article_id}.txt` 생성, 메타데이터 JSONL의 `content.uri`가 참조 + `structData` | 본문 검색 품질이 좋음, 파일 수가 조 개수만큼 |
| B. 구조화 데이터 | 조문 본문을 `structData`의 문자열 필드(`body`)로 넣은 구조화 JSONL, 스키마에서 검색·필터 가능 필드 지정 | 파일 1개로 단순, 본문 검색 가중 설정 필요 |

- **시험 순서**: 안 B(단일 구조화 JSONL — 생성·검수·재색인·롤백이 단순)를 먼저 시험한다. 성공 기준을 모두 통과하면 안 A는 시험하지 않고 전체 색인으로 진행, 실패하면 안 A를 시험한다.
- **시험 데이터는 실제 학사 규정**으로 한다: 학칙, 휴·복학, 성적·학사경고, 장학 관련 규정에서 조문 20개(규정당 약 5개). 법인 정관(`docs/참고/reg195_2365.hwp`)은 파서 픽스처 용도로만 쓴다 — 학사 규정의 표·부칙·예외 패턴을 대표하지 못하기 때문.
- 시험 규정에서 `<표>` 치환 때문에 **핵심 요건(기준표 등)이 사라지면** 그 규정은 `hwp5html` 또는 로컬 LibreOffice로 표 내용을 추출하는 경로를 즉시 확정한다.

**사전 검증 성공 기준**(조문 20개)
1. 가져오기 성공
2. `access="public"` 필터 동작
3. 대표 질문 5개 중 **4개 이상** 기대 조문이 상위 5개 안(Recall@5)
4. 검색 결과에서 본문·원문 URL·부서·개정일을 복원 가능
5. 같은 ID 재가져오기 시 갱신(덮어쓰기) 방식 확인
6. **정확 인용률**: 대표 질문 결과에서 반환된 본문이 원문 조문과 일치(잘림·병합 없음)
7. **표·부칙 보존율**: `has_table` 표시와 부칙 분리가 검색 결과 메타데이터에 그대로 남음
8. **재색인 시간** 기록(전체 재가져오기 소요)

- 판정은 **1~8을 함께** 본다. Recall@5 하나만으로 안 A 시험을 생략하지 않는다(#410). `structData.body`가 실제 검색 본문으로 어떤 품질로 색인되는지가 핵심이다.

- 결정한 형식과 명령을 이 절에 기록하고 전체 가져오기에 사용한다.
- **색인 버전**: 가져오기마다 `index_version`(예: `articles-v3`)과 가져오기 작업 ID를 매니페스트에 기록. 전체 재색인은 새 데이터 스토어(또는 버전 필터)로 만든 뒤 검증 후 전환하고, 기존 색인을 바로 덮어쓰지 않는다.
- 검색 시 필요한 필터: `access = "public"`, (선택) `kind = "main"`
- 부칙은 기본 검색에서 가중치를 낮추고, 질문에 "시행일·경과·언제부터"가 있으면 포함

## 6. 실시간 데이터 캐시

인스턴스 메모리 캐시(프로세스 내 dict + 만료 시각) + 실패 시 마지막 정상값 반환.

| 키 | TTL | 마지막 정상값 보관 |
|---|---|---|
| `notices:{board}` | 30분 | 예(최대 7일) |
| `calendar:{year}` | 24시간 | 예 |
| `menu:{date}` | 6시간 | 예(당일만) |

인스턴스가 여러 개면 캐시가 인스턴스별로 따로 생기지만 읽기 전용 공개 데이터라 문제없다.

**오래된 값(stale) 사용 제한**
- 마지막 정상값을 쓸 때는 `ToolResult.stale=true`, `as_of`, `age_seconds`를 반드시 채운다(03 문서).
- **마감·신청기간·"오늘"·"지금" 질문**에서는 stale 공지·일정을 **확정 답변의 근거로 쓰지 않는다** — "○월 ○일 기준 마지막 확인 정보"로만 보여 주고 원문 재확인을 안내한다(compose 규칙, 02 문서).
- 식단은 다른 날짜의 캐시를 절대 대신 쓰지 않는다.
