## 0. 원칙

1. **매일 저녁, 동작하는 End-to-End가 있어야 한다.** 기능을 옆으로 넓히기 전에 "질문 → 답"이 끝까지 도는 가장 얇은 줄기를 1~2일차에 먼저 만든다.
2. **심사 기준에 맞춰 만든다.** 평가는 "기능 수"보다 **Agent다운 문제 해결 과정과 실제 동작**이다. 그래서 UI에 **Agent의 판단 과정(어떤 도구를 왜 불렀는지)을 실시간으로 보여주는 타임라인**을 넣는다. 시연영상 요건(입력 → 판단 → 도구 실행 → 결과)을 화면 자체가 보여주게 한다.
3. **개발기간 내 개발을 증빙한다.** 9/29에 새 git 저장소를 만들고 첫 커밋부터 자주 커밋한다. AI 도구·오픈소스·데이터 출처는 `docs/ai-usage-log.md`에 그날그날 기록한다(별지2 신고서 작성용).
4. **신청서와 어긋나지 않게 한다.** 신청서에 적은 스택(Gemini·LangChain·Vertex AI Search·FastAPI·Firestore·Cloud Run)을 기본으로 하고, 바꿔야 하면 이유를 보고서에 남긴다.

## 1. 전체 구조

```
[웹 챗 (HTML/JS, 모바일)]  ──SSE──▶  [FastAPI on Cloud Run]
   · 답변 + 근거 카드                     │
   · Agent 판단 타임라인                  ▼
   · 👍/👎 피드백                  [LangGraph Agent]
[관리자 대시보드]                  classify → (ask_user) → act(도구 루프)
   · 미응답 질문                          → compose → verify → answer | fallback
   · 피드백 통계                          │
                                          ├─ search_academic_knowledge ──▶ Vertex AI Search (규정 조 단위 색인)
                                          ├─ get_notices ───▶ 게시판 RSS (캐시 30분)
                                          ├─ get_academic_calendar / get_menu ─▶ 공개 페이지 (캐시)
                                   [Firestore]  대화 로그·피드백·미응답 질문
                                   [Cloud Storage] 규정 원문(HWP)·변환 텍스트
                                   [Cloud Scheduler] 규정 버전 점검(일 1회)·공지 수집
```

- 모델: **Gemini (Vertex AI)** — MatchProf에서 쓰는 `gemini-3.5-flash`를 기본으로 한다.
- Agent 프레임워크: **LangChain + LangGraph** (`langchain-google-vertexai`, `langgraph`).
- **Cloud Run은 상태를 두지 않는다(stateless).** 대화 상태는 Firestore에 저장하므로 재시작·재배포·인스턴스 증가에도 대화가 이어진다(4-4절).

### 3-1. 규정 (핵심 데이터)

| 단계 | 방법 | 비고 |
|---|---|---|
| 목록 수집 | 규정관리시스템의 편별 목록 페이지 파싱 → 규정명·규정번호·개정일·개정차수·소관부서·HWP URL | 대상: **제2편 학칙, 제3편 학사행정** 우선, 이후 장학·학생생활 관련 규정 추가 |
| 다운로드 | `/rule/rdata/…/reg{번호}_{버전}.hwp` | 요청 간격 1초 이상, `data/raw/`에 보관 |
| 텍스트 변환 | **pyhwp(`hwp5txt`)** | 경진대회 공고문 HWP로 동작 확인됨. 실패 파일만 LibreOffice로 대체. **라이선스 확인 필요(AGPL-3.0로 알고 있음)** — 색인 파이프라인의 변환 도구로만 쓰고 서비스 코드·저장소에 포함하지 않는다 |
| 조 단위 분할 | 3-2 파싱 규칙 참조. 장·절 제목은 메타데이터로, **부칙은 별도 ID 체계**, 별표·별지 서식은 제외 | 2,000자 초과 조는 항(①②…) 단위 서브 청크 |
| 메타데이터 | `article_id`, 규정명, 조 번호·가지번호·제목, 장·절, 개정일, 개정차수, 소관부서, 규정 위계, 원문 URL, `has_table`, `access`(public/internal) | 이 필드가 곧 **근거 인용**의 재료 |
| **검색 사전 검증** | 전체 변환 전에 **조문 20개로 먼저** 가져오기 → 대표 질문 5개로 기대 조문 검색 확인 → 성공한 스키마·명령 고정 | 전체를 변환한 뒤 형식 오류를 발견하는 위험 제거 (아래 필드) |
| 색인 | **Vertex AI Search**에 조 1개 = 문서 1개(JSONL: 본문 + structData)로 가져오기 | 사전 검증에서 고정한 스키마로 전체 가져오기. 기다리는 동안 다음 작업(도구 구현) 진행 |
| 버전 감지 | 목록의 버전 번호 + **본문 해시**를 매니페스트와 비교 → 바뀐 규정만 재변환·재색인 | Cloud Scheduler 일 1회. "부서가 규정만 고치면 자동 반영"의 근거. 매니페스트 규칙은 3-6절 |

**색인 문서 필드**: `article_id`, `content`(조문 본문), `rule_name`, `article_no`, `article_branch`, `article_title`, `chapter`, `department`, `revision_date`, `revision_no`, `rule_level`(위계), `source_url`, `has_table`, `access`, `content_hash`

### 3-2. HWP 조문 파싱 규칙

**`article_id` 체계** — 본문 제1조와 부칙 제1조의 충돌 방지

| 구분 | 형식 | 예 |
|---|---|---|
| 본문 | `{규정번호}_main_{조}[_{가지}]` | `101_main_32`, `101_main_12_2`(제12조의2) |
| 부칙 | `{규정번호}_add_{시행일 YYYYMMDD}_{조}` | `101_add_20240301_1` |
| 서브 청크 | 위 ID + `_p{항번호}` | `101_main_32_p2` |

**조 머리 정규식**: `^제\s*(\d+)\s*조(?:\s*의\s*(\d+))?\s*\(([^)]+)\)`
- `제12조(수강신청)` → 조 12, 가지 없음, 제목 "수강신청"
- `제12조의2(수강철회)` → 조 12, 가지 2, 제목 "수강철회"
- 부칙 구간은 "부칙" 머리와 시행일 표기를 기준으로 나누고, 그 안의 조는 부칙 ID로 발급

**표 처리**
- `hwp5txt`는 표의 열 순서가 꼬일 수 있어 LLM이 오독할 위험이 있다.
- 표가 들어 있는 조는 본문 텍스트만 색인하고 `has_table: true`를 표시한다.
- `has_table` 조를 근거로 쓸 때는 답변에 "세부 기준표는 원문 확인 필요"를 넣고, 근거 카드에 **원문(HWP) 링크를 반드시** 붙인다.

**검수**: 규정별 조 개수·조 번호 연속성·부칙 분리 여부를 자동 점검하는 스크립트 + 전지원 샘플 검수.

### 3-3. 로컬 하이브리드 검색 (대안)

Vertex AI Search로 진행한다. **전환은 사용자(김진)에게 보고하고 승인을 받은 경우에만** 한다. 시간 기준은 두지 않는다 — 순서대로 진행하다가 색인 단계에서 막히면 그때 보고한다.

- **판단 조건**: 사전 검증(조문 20개)에서 데이터 스토어가 활성 상태이고, 대표 질문 5개에 기대 조문이 상위 5개 안에 나오는가
- **전환 절차**: 판단 조건을 충족하지 못하면 원인을 파악해 **사용자에게 보고**(증상·원인·시도한 조치·전환 시 영향)하고, **승인하면 전환**한다. 승인 전에는 임의로 전환하지 않는다. 전환 사실·사유·승인 일시는 `ai-usage-log.md`와 완료보고서에 기록
- **대체 스택**
  - 키워드: `rank-bm25` + **한국어 형태소 분석기(`kiwipiepy`)** — 띄어쓰기 기준 분리로는 "휴학을/휴학은/휴학하려면"이 서로 다른 단어가 되어 검색이 되지 않으므로 필수
  - 의미 검색: Vertex AI 임베딩(**착수 시점의 최신 임베딩 모델 확인**) + 코사인 유사도, 조 수천 개라 메모리로 충분
  - 결합: RRF(Reciprocal Rank Fusion), `score = 1/(60 + rank_bm25) + 1/(60 + rank_dense)`
- **보고서 기재**: 전환하면 **실제 이유(색인 지연·오류)를 그대로** 적는다. 사후에 다른 명분으로 포장하지 않는다.

## 4. Agent 설계 (LangGraph)

### 4-1. State

```python
class State(TypedDict):
    messages: Annotated[list, add_messages]
    profile: dict            # 학년, 학적(재학/휴학), 장학 수혜, 학과 — 대화 중에만 유지
    intent: str              # rule | procedure | notice | calendar | menu | location | out_of_scope
    missing_slots: list[str] # 절차 안내에 필요한데 모르는 조건
    evidence: list[dict]     # 도구가 가져온 근거(조문·공지·일정), 각 항목에 id 부여
    draft: dict              # {sentences:[{text, cite_ids, supporting_quotes}], checklist:[{text, cite_ids}], next_actions:[...]}
    pending_question: dict | None  # 직전 턴에 되물은 내용(Firestore에서 복원)
    verified: bool
    access: str              # public | internal (로그인 여부)
```

### 4-2. 그래프

```
START → load_state → classify ──┬─ out_of_scope ─────────────────────────▶ fallback → save_state → END
          (Firestore)           ├─ procedure & missing_slots ─▶ ask_user ─▶ save_state → END (질문을 던지고 턴 종료)
                                └─ 그 외 ─▶ act (도구 호출 루프, 최대 4회)
                                   ↓
                               compose (구조화 출력: 문장별 cite_ids)
                                   ↓
                               verify ── 남은 문장 0개 ─▶ fallback → save_state → END
                                   ↓ (검증 실패 문장·체크리스트 항목 제거)
                               answer → save_state → END
```

| 노드 | 역할 | 구현 포인트 |
|---|---|---|
| `classify` | 의도 분류 + 절차 질문이면 필요한 조건(slot) 판단 | Gemini 구조화 출력(Pydantic) |
| `load_state` / `save_state` | Firestore의 대화 상태 읽기·쓰기 | 4-4절 |
| `ask_user` | 모르는 조건을 한 번에 되물음 ("학년과 장학금 수혜 여부를 알려 주세요") | 질문을 보내고 **턴을 끝낸다**. `pending_question`·`missing_slots`를 저장해 두고, 다음 메시지가 오면 `classify`가 이를 읽어 답을 `profile`에 채운 뒤 이어서 처리. 요청 사이에 걸친 `interrupt()`는 쓰지 않는다(재시작 시 유실 위험) |
| `act` | 도구 선택·호출. 규정 + 공지 + 일정처럼 **여러 도구를 연달아** 부를 수 있음 | `ToolNode` + 도구 바인딩된 모델, 반복 상한 4 |
| `compose` | 근거만으로 답 작성. **모든 문장·체크리스트 항목에 `cite_ids`**, 문장마다 근거 원문의 짧은 구간 **`supporting_quotes`** 를 달게 함. 절차 질문이면 체크리스트·다음 행동 포함 | 구조화 출력 |
| `verify` | **코드로 결정적 검증** (4-5절 규칙). 실패한 문장·항목은 삭제, 남은 문장이 없으면 fallback | "근거 인용 포함률 100%"와 환각 억제의 근거 |
| `fallback` | "확인된 규정을 찾지 못했습니다" + 가장 관련 있는 **소관부서 안내**(이름·대표 전화) + 미응답 질문 기록 | 환각 억제 지표의 근거 |

- **Memory**: 대화별(`thread_id`) 최소 상태를 **Firestore에 저장**한다(4-4절). 로컬 개발에서는 `MemorySaver`를 써도 되지만, 배포본은 요청마다 Firestore에서 읽고 응답 후 저장한다.
- **Feedback**: 👍/👎와 미응답 질문을 Firestore에 저장 → 대시보드 → 이동우의 휴먼 피드백과 함께 **프롬프트·분할 규칙·동의어 개선**에 반영(개선 전후 수치를 보고서에 기록).
- **스트리밍**: `graph.astream(stream_mode="updates")`로 노드 진행 상황을 SSE로 내보내 UI 타임라인에 "의도 파악 → 학칙 검색(3건) → 학사공지 확인 → 근거 검증 통과"처럼 표시한다. 근거 카드는 도구 실행 직후 먼저 보내고, **답변 본문은 verify가 끝난 뒤 한 번에** 보낸다(검증 전 문장을 먼저 내보내면 나중에 삭제될 문장이 화면에 보이기 때문). 이벤트 규격은 5-1절.

### 4-3. 대표 시연 시나리오 (End-to-End)

> 학생: "휴학하려고 하는데 어떻게 해요?"
> Agent: (의도=절차, 조건 부족) "학년과 이번 학기 장학금 수혜 여부를 알려 주세요."
> 학생: "2학년이고 장학금 받고 있어요."
> Agent: 학칙 휴학 조항 검색 → 장학 규정 검색 → 학사공지(휴학 신청 기간) 조회 → 학사일정 조회 → 근거 검증
> → **체크리스트**: 신청 기간·방법·서류 / **주의**: 장학금 관련 규정(해당 조항 인용) / **근거 카드**: 학칙 제○조(개정일·소관부서·원문 링크) / **담당 부서**: 학사 담당 부서(이름·대표 전화)

이 시나리오 하나로 되묻기, 다중 도구 호출, 근거 검증, 체크리스트, 담당 부서 안내가 모두 드러난다. 시연영상은 이 흐름을 중심으로 만든다.

### 4-4. 대화 상태 저장 (Firestore)

`min-instances=1`은 콜드 스타트를 줄일 뿐 메모리 보존을 보장하지 않는다. 배포할 때마다 인스턴스가 교체되므로, 되묻기 도중 상태가 사라지지 않게 **최소 상태만 명시적으로 저장**한다.

```text
threads/{thread_id}
  profile            # 학년·학적·장학·학과
  pending_question   # 직전에 되물은 질문과 원래 질문
  missing_slots
  last_intent
  updated_at
  expires_at         # TTL — 오래된 상태 자동 삭제(예: 24시간)
```

- 긴 대화 전체를 복원하지 않고 절차 안내에 필요한 것만 저장한다.
- 이 덕분에 Cloud Run 인스턴스 수를 1개로 묶을 필요가 없다.

### 4-5. 인용 검증 규칙 (verify 노드)

`cite_id`가 존재하는지만 보면 **엉뚱한 조문 ID를 붙인 틀린 문장도 통과**한다. 다음을 모두 코드로 검사한다.

1. `cite_ids`가 이번 턴의 `evidence`에 실제로 있어야 한다.
2. `supporting_quotes`가 인용한 근거 본문에 **실제로 포함**되어야 한다. 비교 전에 공백·문장부호·전각/반각을 **정규화**한다(LLM이 구간을 옮기며 띄어쓰기를 바꾸는 일이 흔해, 정규화 없이 비교하면 멀쩡한 문장까지 지워짐).
3. 문장에 들어 있는 **날짜·금액·학점·횟수·기한 같은 숫자 사실**은 인용한 근거 본문에 같은 값이 있어야 한다.
4. 근거가 없는 **체크리스트 항목**도 삭제한다.
5. 남은 문장이 없으면 fallback.

- 원문과 요약 사이의 **의미 일치**는 코드로 판정할 수 없으므로 평가 단계에서 LLM 채점 + 사람 확인으로 따로 측정한다(6절 Faithfulness).

### 5-2. 화면

- **웹 챗**: 순수 HTML/CSS/JS, 모바일 우선. 답변 아래 **근거 카드**(규정명·조·개정일·소관부서·원문 링크)와 접을 수 있는 **판단 타임라인**.
- **추천 질문 칩**(시작 화면): 기능 5개를 하나씩 시연하도록 구성 — 시연·심사 때 입력 실수를 줄인다.
  - `휴학 신청 절차 안내` → 되묻기·체크리스트
  - `성적 경고 기준과 재수강` → 규정 근거 인용
  - `오늘 학생식당 메뉴` → 실시간 도구
  - `장학금 신청 언제까지예요?` → 규정 + 장학공지(위치 기능은 제외 — #461)
  - 범위 밖 질문 1개 → fallback·담당 부서 안내
- **[새 대화 시작] 버튼**: 새 `thread_id` 발급(브라우저 저장), 이전 대화의 학생 조건이 다음 상담에 섞이지 않게 한다.
- **관리자 대시보드**: 미응답 질문 목록(빈도순), 👎 답변, 일자별 질문 수. 부서에는 "보기만 하는 참고자료".
- **재학생 인증: 하지 않음**(11절 참조). 학생 화면은 로그인 없이 쓴다. 관리자 페이지는 **Google 로그인 + 허용 이메일**로 보호한다(#450~#457 — 교내 문서 업로드·강제 재수집 권한 때문).

### 5-3. 개인정보·보안

- 입력창에 **"학번·성명·전화번호 등 개인정보를 입력하지 마세요"** 안내 + 간단한 처리방침 페이지.
- 저장 전에 학번·전화번호·이메일 패턴을 **마스킹**한다.
- 저장은 통계·개선에 필요한 최소한으로 한다(질문, 의도, 검색된 조 id, 응답 결과 유형, 피드백). **보존 기간**(예: 대회 종료 후 90일)과 삭제 방법을 처리방침에 명시.
- Firestore는 서버 서비스 계정만 접근한다. 인증은 키 파일 대신 **Cloud Run 서비스 계정 + ADC**.
- 관리자 인증은 Google 로그인(허용 이메일, 서버 ID 토큰 검증) — 공유 관리자 키 폐기. `.env`·키 파일·승인 문서 원문은 Git에 넣지 않는다.
- 외부 콘텐츠 처리 규칙(허용 도메인, SSRF 방지, 프롬프트 인젝션 방어)은 3-4절.

## 6. 평가 설계 (목표 성능 ↔ 측정 방법)

| 신청서 목표 | 측정 |
|---|---|
| 테스트셋 50문항 정답률 85% 이상 | `eval/testset.jsonl`(질문, 기대 근거 조 id, 핵심 사실 목록, 유형). 아래 판정 기준 5개를 모두 충족해야 정답. **보고 수치는 최종 평가셋(15문항) 기준**을 함께 제시 |
| 근거 인용 포함률 100% | 답변 문장 중 검증을 통과한 인용이 붙은 비율 (verify 로그로 자동 계산) |
| 근거 없는 질문의 "모름 + 부서 안내" 90% 이상 | 범위 밖 질문 10개 별도 세트 → fallback 비율 |
| 공지 반영 1시간 이내 / 응답 10초 이내 | 캐시 TTL 30분 / 응답시간 p50·p95 기록 |
| 사용성 긍정 80% 이상 | 재학생 5~10명 간단 설문(이동우 진행) |

**테스트셋 분리** — 50문항 전체를 보며 튜닝하면 수치가 과적합되므로 나눈다.

| 세트 | 문항 | 용도 |
|---|---|---|
| 개발셋 | 35 | 검색·프롬프트 개선에 반복 사용 |
| **최종 평가셋** | 15 | **개발 중에는 정답을 보며 튜닝하지 않는다.** 6일차 이후 최종 수치 산출용 |
| 범위 밖 | 10 | fallback 평가 전용 |

- 유형 배분(두 세트에 고르게): 규정(휴학·복학·수강·성적·졸업·장학), 공지·일정, 절차(되묻기). (위치 질문 유형 없음 — 위치 기능 제외, #461)
- 세트 분리는 이동우가 작성 직후 확정하고, 최종 평가셋 파일은 튜닝 작업 중에 열어 보지 않는다.

**문항별 판정 기준** — 5개를 모두 충족해야 정답

1. 기대 조문 검색 성공(상위 5개 안)
2. 핵심 사실 포함
3. 잘못된 사실 없음
4. 유효한 인용 포함
5. 필요한 다음 행동 또는 담당 부서 포함

- LLM 채점은 1차 자동 판정, **오답·경계 사례는 이동우가 수동 확정**. 보고서에는 자동 판정과 수동 확정 결과를 **구분해** 적는다.

**추가 지표**

| 지표 | 의미 |
|---|---|
| Retrieval Recall@5 | 기대 조문이 검색 상위 5개에 드는 비율 — 틀렸을 때 검색 문제인지 생성 문제인지 가름 |
| Verified Retention | 답변 초안 문장 중 검증을 통과해 살아남은 비율(상세설계 06 — 구 Citation Coverage) |
| Citation Precision | 인용이 실제로 그 문장을 뒷받침하는 비율(표본 수동 확인) |
| Faithfulness | 답변이 근거 범위를 벗어나지 않는 비율(LLM 채점 + 수동 확인) |
- 4일차부터 매일 저녁 평가를 돌려 수치 추이를 남긴다 → 보고서의 "테스트·성과" 절 재료.

**평가 실행 제어 (호출 한도·비용 방어)**
- 동시 실행 상한 `asyncio.Semaphore(3)`, 질문 간 300ms 간격
- 429·5xx는 공통 재시도 래퍼(지수 백오프 + 지터, 최대 5회)로 처리 — 10-2절
- **결과 캐시**: `eval/cache/{질문해시}_{git 커밋}_{색인 버전}_{모델}.json`. 커밋이나 색인이 바뀌면 캐시가 무효가 되어야 **개선·퇴보가 수치에 드러난다**(질문 해시·모델만으로 키를 만들면 옛 결과가 재사용되어 비교표가 무의미해짐)

## 7. 8일 실행 계획 (담당·완료 기준)

## 10. MatchProf에서 가져오는 기법·교훈

MatchProf 운영에서 검증된 기법을 적용한다. **코드는 복사하지 않고 설계만 가져온다**(사전 개발 금지 규정).

### 10-1. 검색 품질

| MatchProf 기법 | campusBridge 적용 | 반영 위치 |
|---|---|---|
| **검색어 확장**(`enhance.py`) + 결과 Firestore 캐시(질문 해시) | 학생 구어 → 규정 용어로 확장. 예: "학교 쉬고 싶어요" → 휴학, "F 받은 과목 다시 듣기" → 재수강. **classify 호출에 통합**(상세설계 02 §4-2, #406 합의) — 문맥 의존이라 질문 해시 캐시는 두지 않음 | classify, 2일차 |
| **범위 밖 질문 판정**(`query_guard`) + 캐시 | `classify`의 `in_scope` 판정(통합 호출 안에서, 캐시 없음) | 2일차 |
| **문서 유형 가중치**(논문·특허 가중) | 규정 위계 메타데이터(학칙 > 규정 > 시행세칙·지침)를 저장하고, 같은 주제면 근거 카드에 위계 표시 | 1일차 메타데이터 |
| **Vertex 응답의 인용 표기 제거**(`_strip_citations`) | Vertex AI Search 요약 기능은 쓰지 않고 조문 원문만 받아 우리 verify 노드로 인용 관리 | 2일차 |

### 10-2. 안정성·성능

| MatchProf 교훈 | campusBridge 적용 | 반영 위치 |
|---|---|---|
| **Gemini 429·5xx 지수 백오프 + 지터 재시도**(429로 키워드 빈 문서 52건 발생 사고) | 모든 Gemini 호출을 공통 래퍼로 감싸기. 특히 **평가 50문항 일괄 실행·색인 준비**에서 필수 | 1일차 공통 모듈 |

| **검색 2단계 분할**(결과 먼저, AI 보강은 나중) | SSE로 **근거 카드를 먼저** 보내고, 검증을 마친 답변을 이어서 보냄 → 체감 속도 개선, 목표 "응답 10초 이내" 대응 | 3일차 |

3. **재학생 인증: 하지 않는다.** 따라서
   - 교내 문서는 **공개 답변에 써도 된다고 승인받은 것만** 색인한다(공문 승인 시 "챗봇 답변에 인용 가능" 범위로 받기).
   - `access` 메타데이터와 검색 필터 코드는 남겨 두되 MVP에서는 전부 public으로 운영한다. 향후 인증을 붙일 확장 지점으로만 둔다.
   - 신청서의 "재학생 인증 후 제공"과 달라지므로, 완료보고서에 "승인 범위를 공개 답변용으로 한정해 인증 없이 운영"으로 변경 사유를 적는다.
4. **GitHub**: 일단 **비공개** 저장소, 나중에 공개로 전환. 공개 전 점검: 비밀키·`.env` 이력 없음, `docs/관련서류/`·`data/raw/` 제외 확인, 승인 교내 문서 원문이 저장소에 없는지 확인. 심사기간에는 심사위원에게 접근 권한을 준다(공고문 요건).
5. **설명회 질문거리**: 보류.
6. **일정은 시간 제약보다 순서**: 각 단계는 순서대로 진행하며, 특정 시각을 기준으로 강제 전환하지 않는다. 검색엔진 전환은 **사용자 승인 후에만** 한다.
